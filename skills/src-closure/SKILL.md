# src-closure — 候选三态收敛

## 核心问题

一个候选线索最后只有三种合法结局。**没有第四种「算了不看了」。**

| 状态 | 判据 | 后果 |
|---|---|---|
| `confirmed` | 有可运行的 PoC；或白盒下完整的 source → control → sink → impact 且可达 | 进 `src-triage` |
| `ruled_out` | 能**点名某个具体位置的具体控制**，并证明它在攻击者可达的**每一条**路径上都先于 sink 执行 | 记入覆盖台账 |
| `open_proof_gap` | 看起来像，但既没证实也没法点名控制 | **必须留档**，不许静默丢弃 |

## 铁律：信息缺失不是安全的证明

以下**全部**属于 `open_proof_gap`，不属于 `ruled_out`：

- 找不到调用方
- 不知道这个服务是否真的部署了
- 服务起不来 / 环境不对
- 只有前端代码，后端看不到
- 试了几个 payload 都没成功
- 「理论上应该有过滤」
- 「现代框架应该默认安全」

**「我没能证明它可被利用」≠「它不可被利用」。**

## ruled_out 的判定式（必须逐条满足）

想判 `ruled_out`，必须能填满这四格：

1. **控制点**：具体在哪个文件/哪行/哪个中间件/哪个 WAF 规则？（不能是「框架层」）
2. **控制内容**：它到底做了什么？（白名单？参数化？转义？类型转换？）
3. **执行顺序**：它是否在**所有**攻击者可达路径上都先于 sink 执行？
4. **覆盖性**：有没有绕过路径？（另一条路由、另一个参数位置、另一种编码、另一个 HTTP 方法）

四格有一格填不满 → 就是 `open_proof_gap`，不是 `ruled_out`。

### 反例对照

| 说法 | 判定 | 原因 |
|---|---|---|
| 「用了 ORM，所以没有 SQLi」 | ❌ open_proof_gap | 没点名哪个调用点、有没有原生 SQL 拼接 |
| 「第 42 行用了 `parseInt` 强制转数字」 | ✅ ruled_out | 点名位置 + 具体控制 + sink 是数值查询 |
| 「试了 `' OR 1=1--` 没报错」 | ❌ open_proof_gap | 没成功 ≠ 不可利用（可能是盲注/编码问题） |
| 「nginx 配置了 `$uri` 规范化，且 location 匹配在 proxy_pass 前」 | ✅ ruled_out | 点名组件 + 具体规则 + 顺序 |
| 「不知道这个 endpoint 有没有被网关保护」 | ❌ open_proof_gap | 信息缺失 |

## 一个根因 ≠ 一个候选

同一条路由上的多个问题，**按 sink / 失效控制点 / 影响**拆分：

- 一个危险 helper 有 6 个调用点，4 个独立可达 → **4 个候选**
- 同一路由上的命令执行 / SSRF / 路径写入 / 鉴权绕过 → **不同漏洞**
- 共享 URL ≠ 共享 bug

反过来，**同一个缺陷被报了两次**（不同 severity、不同措辞、同一 PoC）→ 是重复，见 `src-triage` 的判重五问。

## 记录格式

每个候选收敛时，写清楚：

```
候选：/api/export 的 filename 参数
状态：open_proof_gap
已做：试了 ../、..%2f、%252e%252e%252f，均 400
缺口：不知道后端是否在写入前做了 basename()；拿不到源码
需要什么才能收敛：源码中 writeFile 调用点前 5 行，或一个成功写出的 PoC
```

`needs_follow_up` 必须带「需要什么才能收敛」，否则下一轮没法接。

## 与定级的关系

收敛状态决定能说什么：

- `confirmed` → 可以定级，但**只给已证实的后果定级**（见 `src-report-writing` 的定级标尺）
- `ruled_out` → 不定级，只记覆盖
- `open_proof_gap` → **不定级、不提交**，但必须出现在覆盖摘要里

## 常见自欺（都会被三家拒）

| 自欺 | 真相 |
|---|---|
| 「响应里出现了我的 payload」 | 回显 ≠ 执行。要看是否在可执行上下文 |
| 「返回了 200，说明成功了」 | 200 可能是 SPA 回退 / 网关错误页 |
| 「扫描器说 high」 | 扫描器不判可达性 |
| 「这个参数看起来危险」 | 看起来 ≠ 可达 |
| 「缺 CSP，所以是 XSS」 | 缺安全头本身是 N/A，不是洞 |
| 「能读到自己的数据，说明有 IDOR」 | 自己的数据不能证明越权，必须有 victim 对照 |

## 与其它 skill 的关系

- `src-coverage`：本 skill 管单个候选，coverage 管 surface 级台账
- `src-triage`：`confirmed` 之后的判重与提交决策
- `src-retest`：提交前的独立复测硬门禁
- `src-report-writing`：报告里的 Counterevidence / Confidence 字段就来自这里
