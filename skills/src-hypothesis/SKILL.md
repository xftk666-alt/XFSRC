# src-hypothesis — 假设与证伪纪律

## 为什么需要它

两个失败模式最烧预算：

1. **确认偏误**：看到「返回 200 且内容不同」就认定是 IDOR，然后花 20 轮去「证明它」。
2. **死磕**：同一个思路失败后换个 payload 再试，连续 10 次都不换轴。

解法不是「更聪明」，是**机械约束**：每个候选必须先写清楚「什么结果会让我放弃」。

## 一个候选的必填结构

发现疑似漏洞时，先写这个（落到 `record_fact`，不要只在脑子里）：

```markdown
## Candidate: <一句话描述>
surface: <URL / 接口 / 功能点>
vuln_class: <taxonomy 里的类名>
taxonomy_ref: <family / priority / payout>

### H1（主假设）
<我认为发生了什么，机制层面>
区分性探针: <一个能区分 H1 与 H2 的具体请求/操作>
预期结果: <H1 成立时，这个探针必须返回什么>
反证条件: <如果探针返回 X，则 H1 不成立>

### H2（竞争假设，必须与 H1 互斥）
<另一种合理解释，通常是"这是设计如此/本来就公开/只是错误页">
区分性探针: ...
预期结果: ...
反证条件: ...

### 若 H1/H2 都被排除
<第三假设，或判定 ruled_out / open_proof_gap 的条件>
```

**硬要求**：
- H1 与 H2 必须**互斥**：不能一个成立另一个也成立。
- 每个假设必须有**一个能区分它的探针**，不能只是「再多测几次」。
- 反证条件必须**可观测**（状态码/字段/长度/时序/OOB 回连），不能是「感觉不像」。

## 三态收敛（与 src-closure 一致）

| 结论 | 允许的证据 | 不允许 |
|---|---|---|
| `confirmed` | H1 的区分性探针命中 + H2 的探针明确未命中 + 实际影响 | 「试了很多次都像」 |
| `ruled_out` | 点名某个具体控制（鉴权中间件/参数校验/公开设计），并证明它在**所有可达路径**上都先于 sink | 「没找到证据」 |
| `open_proof_gap` | 明确写出缺什么证据、为什么现在拿不到 | 静默丢弃、或硬写成 confirmed |

**「没找到证据」不是「不存在」。** 信息缺失一律记 `open_proof_gap`。

## 换轴规则（防死磕）

满足任一条就必须换轴，不得继续同一思路：

1. 同一候选连续 **3 次**探测都没有新信息。
2. 同一个 payload 变形试了 **3 种**仍无差异。
3. 已经能解释当前结果的最简假设是「设计如此」，且没有新证据推翻它。
4. 单候选消耗超过任务预算的 **1/4**。

换轴选项（按顺序）：
- 换 surface（同族、不同接口）
- 换族（同 surface、不同风险类，见 `src-taxonomy`）
- 换身份（低权/管理员/未登录）
- 换时间窗（竞态/缓存过期）
- 记 `open_proof_gap` 并转下一个

## 与工具的关系

- 区分性探针优先用 `diff_replay`（多身份对照）和 `http_evidence_record`（带 expect 的断言），不要用「我自己看返回」。
- 每次探针都要留证据包；没有证据包的探针等于没做。
- 探针结果写回 fact 后，`src-closure` 用三态判定。

## 输出模板（给报告用）

报告里必须有 Counterevidence 段，直接引用 H2 的探针结果：

```markdown
## Counterevidence
- 竞争假设 H2：该接口设计为公开。探针：匿名请求同一 URL → 401，H2 排除。
- 另一竞争假设：返回的是当前用户而非 URL 中的 ID。探针：用 A 的 token 请求 B 的 ID → 返回 B 的 email，H2' 排除。
```

这一段 `report_check` 会强制检查，写不出就说明还没收敛。
